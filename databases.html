1. Description, Purpose and Boundaries

Protect integrity, tenant isolation and recoverability across storage layers.

Choose storage by consistency, query patterns, tenancy and recovery requirements. Start with the data lifecycle before selecting a product.

Treat databases & storage as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Apply constrained schema and versioned migrations. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize cross-tenant queries omit membership filter and migration locks or rewrites large tables. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, verify tenant isolation and restore backups, rather than merely observing request acceptance.

5. Detailed Mechanics and Topic Features

Storage types

Relational databases suit structured records, joins, constraints and transactions. Document stores suit evolving aggregate documents. Key-value stores suit simple lookups and caches. Object storage holds files and exports. Vector indexes support similarity retrieval; retain authoritative records separately. Search indexes support text discovery. Time-series and analytical stores support event analysis. A cache or search index should not silently become the only copy of critical data.

Cloudflare reference mapping

D1 provides SQL storage for Workers applications; R2 holds objects; KV supports distributed key-value access; Durable Objects can coordinate state and concurrency. Evaluate each service’s current consistency and transaction semantics before choosing it for sessions, OTP counters or locks. Keep development, demo, staging and production resource identifiers separate. Bind resources to the backend; never place database credentials in public HTML.

Schema and integrity

Model users, identities, memberships, roles, sessions, auth_challenges, email_outbox, delivery_events and audit_events. Include tenant_id where applicable, creation and expiry timestamps, unique identity constraints, foreign keys and indexes matching real queries. Authorize tenant access server-side on every operation. Use parameterized queries. Define deletion, retention and export rules before collecting sensitive data.

Implementation and verification

Document access patterns → select store → define schema and constraints → apply versioned migrations → provision least-privilege bindings → implement repository/query layer → test isolation and concurrent writes → rehearse restore. Use additive migrations before destructive changes. A backup is useful only after a restore test; define recovery-point and recovery-time objectives. Measure query plans and latency before adding indexes or caches.

7. Detailed Mermaid Architecture, Process and Explanations

This flow describes the request lifecycle, security checks, execution, retries and durable evidence for this chapter. It is implementation guidance, not a deployed-system claim.

What each stage does

  1. 1. Receive tenant-scoped data operation: Capture caller, purpose, tenant or user identifier, correlation ID and data classification.
  2. 2. Check schema and row ownership: Apply prerequisite checks before initiating any irreversible action.
  3. 3. Start transaction and enforce constraints: Enforce the listed restrictions on the server; test valid, expired, repeated and cross-tenant requests.
  4. 4. Commit durable state with version: Perform only explicitly permitted work using short-lived credentials and bounded timeouts.
  5. 5. Audit mutation and monitor latency: Save the state transition and capture a durable operation or idempotency identifier.
  6. 6. Verify backup and restore evidence: Prove the resulting behavior with redacted audit records and automated acceptance tests.
  7. 7. Failure and rollback: Do not blindly repeat side effects. Reconcile committed work, cap retries, and raise incidents when the state is uncertain.

10. Operations, Ownership and Maintenance

Assign a technical owner for databases & storage. Review changes to D1, PostgreSQL, R2 against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.

Recommended implementation sequence

  1. Confirm requirements, data classification, identity boundary and system owner.
  2. Select one primary platform for each responsibility; document alternatives and why they are needed.
  3. Configure development and staging resources separately; store secrets in a server-side secret manager.
  4. Implement the feature with input validation, authorization, timeouts, idempotency and structured error handling.
  5. Test success, denial, expiry, retry, outage, tenant-isolation and recovery scenarios.
  6. Deploy through reviewed CI/CD, verify health and record configuration versions and rollback evidence.

Benefits and security considerations

Benefits: clear service boundaries, repeatable setup, provider-supported integrations, measurable testing and easier maintenance. Security: least privilege, secret isolation, tenant-scoped access, signed callbacks/webhooks, rate limits, dependency review, redacted audit logs and documented key rotation.
