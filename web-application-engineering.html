1. Purpose and system boundaries

This chapter is a practical map for building a production web application. It explains how the browser, identity provider, application backend, database, file storage, email, external APIs and deployment pipeline work together. It is a vendor-neutral blueprint with a Cloudflare-first reference implementation and AWS SES email integration example.

Separate product requirements from provider choices. A brand or logo below is a reference to official documentation, not an endorsement or evidence that the service is enabled in a particular account.

2. Reference architecture and request lifecycle

Request sequence: resolve DNS and TLS; deliver frontend; validate session and CSRF protections; authorize API operation against tenant and resource; validate input; apply business rules; persist transaction; enqueue side effects; return a traceable response; process asynchronous work; record redacted operational evidence.

5. End-to-end implementation process

  1. Discover: define users, jobs-to-be-done, accessibility, data classification, compliance boundaries, success metrics and non-goals.
  2. Design: map journeys, wireframes, responsive states, navigation, design tokens, empty/error/loading states and content model.
  3. Model: define entities, tenant ownership, relationships, constraints, indexes, retention, audit events and migration strategy.
  4. Choose architecture: select frontend, backend runtime, identity, database, storage, queues, email, observability and deployment platform using a decision record.
  5. Build UI: semantic HTML, accessible controls, validation feedback, keyboard navigation, mobile layouts and resilient loading states.
  6. Build backend: route handlers, schemas, authentication middleware, authorization policies, domain services, repository/data access and consistent errors.
  7. Integrate: use server-side secrets, provider SDKs, signed webhooks, timeouts, retries, idempotency and circuit-breaker behavior where appropriate.
  8. Test: unit, integration, end-to-end, accessibility, security, migration, load and recovery tests.
  9. Release: code review, CI gates, migration plan, staged deployment, smoke tests, monitoring and rollback plan.
  10. Operate: patch dependencies, review access, rotate keys, restore backups, inspect incidents and periodically re-evaluate cost and architecture.

6. Identity, authentication, Duo, SSO and sessions

Authentication answers who the user is; authorization decides what that identity may do. Keep both checks server-side on every protected operation. Prefer standards-based federation (OIDC or SAML) when using an identity provider; use WebAuthn for passkeys; use email OTP only with short expiry, rate limits and one-time redemption.

OIDC / OAuth 2.0Federated login and delegated API accessAuthorization Code + PKCE, state, nonce, issuer/audience/signature/expiry validation, exact redirect URIs and minimum scopes.
SAML 2.0Enterprise browser federationMetadata, entity ID, ACS URL, signed assertions, audience, recipient, InResponseTo, time bounds and replay protection.
WebAuthn / passkeysPhishing-resistant public-key authenticationServer-generated challenge; exact origin/RP ID; credential and signature verification; safe recovery and credential revocation.
Email OTPPossession check and account recoveryCSPRNG code, keyed digest at rest, purpose/session binding, TTL, attempt limits, single use, resend cooldown and abuse monitoring.
Cisco DuoSecond factor after primary authentication, or Duo SSO federation in a separate integrationDuo Web SDK v4 Universal Prompt for post-primary MFA; OIDC Auth API where no SDK; Duo SSO OIDC/SAML for federation. Do not conflate these products.
Application sessionMaintain authenticated stateRotate session after login/privilege changes; Secure, HttpOnly, SameSite cookies; CSRF defenses; idle/absolute expiry; revocation and audit.

Role-specific policy example: administrators may be restricted to Duo Push or a separately controlled email OTP; ordinary users may use passkeys or email OTP. The application must enforce this policy at the server and identity-provider policy layer; hiding a button is not enforcement.

7. Backend, APIs, databases, files and integrations

Backend service responsibilities

Keep HTTP routing thin. Validate input at the boundary; invoke domain services; enforce authorization and tenant scope; use transactions for related writes; isolate provider calls behind adapters; return stable status codes and correlation IDs.

API styles

  • REST: resource-oriented HTTP endpoints; document OpenAPI schemas and versioning.
  • GraphQL: client-selected data graph; enforce field-level authorization, query complexity limits and resolver budgets.
  • gRPC: typed RPC, commonly internal service-to-service; manage protobuf compatibility and transport security.
  • Webhooks: verify provider signatures and timestamps, deduplicate event IDs, acknowledge quickly and process durable work asynchronously.

Data and storage choices

  • Relational: Cloudflare D1 (SQLite semantics), PostgreSQL, MySQL; use constraints, migrations, prepared statements and backups.
  • Key-value/cache: Workers KV, Redis; do not treat eventually consistent caches as transactional truth.
  • Object storage: Cloudflare R2 or Amazon S3 for uploads; validate content, size, ownership and malware scanning needs; use short-lived signed URLs.
  • Queues/workflows: Cloudflare Queues, AWS SQS, managed workflow engines; idempotent consumers, bounded retries and dead-letter review.

8. Security, privacy and resilience controls

  • Threat model assets, trust boundaries, abuse cases and data flows before implementation.
  • Use TLS, secure headers, CSP, input validation, output encoding and parameterized SQL.
  • Apply least privilege to service bindings, IAM roles, database access and deployment tokens.
  • Keep secrets in platform secret stores; never commit .env values, private keys, OTPs or provider tokens.
  • Protect against CSRF, XSS, SSRF, SQL injection, IDOR/BOLA, request smuggling, replay and brute force.
  • Use tenant-aware authorization on every object access; never trust a tenant ID supplied only by the browser.
  • Encrypt sensitive data in transit and at rest; minimize PII, set retention/deletion policies and redact logs.
  • Use rate limits, request/body limits, timeouts, idempotency and safe retry policies.
  • Back up data and rehearse restoration; monitor queue age, error rate, latency, spend and provider outages.
  • Review dependency provenance, vulnerability alerts, license terms and software bill of materials.

src/index.ts — Worker API 
interface Env { DB: D1Database }
export default {
  async fetch(request: Request, env: Env): Promise {
    const url = new URL(request.url);
    if (request.method === "GET" && url.pathname === "/api/health") {
      return Response.json({ ok: true });
    }
    if (request.method === "GET" && url.pathname === "/api/items") {
      const result = await env.DB.prepare(
        "SELECT id, title FROM items ORDER BY id DESC LIMIT ?"
      ).bind(50).all();
      return Response.json({ items: result.results });
    }
    return Response.json({ error: "Not found" }, { status: 404 });
  }
} satisfies ExportedHandler<Env>;
SQL migration 
CREATE TABLE IF NOT EXISTS items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  tenant_id TEXT NOT NULL,
  title TEXT NOT NULL CHECK(length(title) BETWEEN 1 AND 200),
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_items_tenant_created
ON items(tenant_id, created_at DESC);

Security note: the example intentionally omits authentication middleware and tenant scoping from the short endpoint illustration. Do not expose the list query publicly in a real multi-tenant application; derive tenant identity from a verified server-side session and bind it in the SQL predicate.

10. Testing, CI/CD and deployment lifecycle

  1. Format, lint and type-check.
  2. Run unit and integration tests against isolated test resources.
  3. Run dependency, secret and static security scans.
  4. Validate database migrations forward and rollback/restore strategy.
  5. Build immutable artifacts and attach commit SHA to deployment.
  6. Deploy preview/staging, run smoke and end-to-end tests.
  7. Approve production promotion; verify health, DNS, TLS and critical user journeys.
  8. Monitor deployment and roll back using a known-good artifact if thresholds fail.

GitHub Actions is a CI/CD orchestrator; Cloudflare Workers deploy through Wrangler; Docker is useful for container workloads but is not required to deploy a Worker. Terraform can manage supported infrastructure resources, subject to provider coverage.
