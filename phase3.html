1. Description, Purpose and Boundaries

Build evidence from representative data before expanding agent behavior.

Treat phase 3: data & prototyping as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Separate development and held-out datasets. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize evaluation leakage and private data copied into public fixtures. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, compare prototype results against human labels, rather than merely observing request acceptance.

7. Detailed Mermaid Architecture, Process and Explanations

This architecture maps the chapter's sequence from intake to validation, recovery and measurable outcome. Decision diamonds represent controls that must be enforced by the implementation, not merely shown in documentation.

Explanation of each process stage

  1. Intake and ownership: Inventory data sources. Check consent licenses and lineage. Record named owner, tenant or data scope, intended beneficiary, and immutable request or change identifier.
  2. Preparation and evidence: Clean deduplicate and partition datasets. Confirm explicit input contracts, measurable success criteria, privacy restrictions, dependencies, and reviewer approval before proceeding.
  3. Control and execution: Build reproducible retrieval prototype. Evaluate quality and leakage. Track the actual state transition and external operations using correlation IDs, least privilege, timeouts, and an idempotency strategy.
  4. Validation: Approve dataset and benchmark version. Compare observed results with acceptance thresholds; reject missing evidence, unauthorized activity, or unexpected output.
  5. Failure and recovery: Stop affected processing, inspect previously committed side effects before attempting a bounded retry, assign a reviewer, and document rollback or manual escalation.
  6. Observability and audit: Store redacted outcomes, configuration and source versions, status, key metrics, owner approval, and evidence links; never expose credentials in site content.

Diagram interpretation: Arrows show the handoff order; Yes and No edges show approval outcomes. A retry is permitted only after reconciling prior side effects. This is a reference design, not a verified live deployment.

10. Operations, Ownership and Maintenance

Assign a technical owner for phase 3: data & prototyping. Review changes to GitHub, Object storage, Evaluation runner against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
