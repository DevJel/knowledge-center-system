1. Description, Purpose and Boundaries

Build evidence from representative data before expanding agent behavior.

Treat phase 3: data & prototyping as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Separate development and held-out datasets. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize evaluation leakage and private data copied into public fixtures. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, compare prototype results against human labels, rather than merely observing request acceptance.

3. Process, Inputs and Outputs

StepActionEvidence
1Collect approved examples with provenanceApproved input scope, source and owner
2Separate development and held-out datasetsRecorded decision, revision and exception handling

Stop at any boundary whose required evidence cannot be established. If an external side effect may already have occurred, reconcile its durable identity before retrying.

10. Operations, Ownership and Maintenance

Assign a technical owner for phase 3: data & prototyping. Review changes to GitHub, Object storage, Evaluation runner against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
