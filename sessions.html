1. Description, Purpose and Boundaries

Enforce permissions and revocation after sign-in on every request.

A successful login must create a controlled, revocable session and enforce access to each resource.

Treat sessions & authorization as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Check tenant, ownership and required permission. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize role changes leave stale permissions and object ids expose another tenant. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, apply mutation and record redacted audit event, rather than merely observing request acceptance.

5. Detailed Mechanics and Topic Features

Session design

Generate high-entropy opaque session tokens; store a digest or keyed verifier server-side with user, tenant, assurance level, issued_at, last_seen_at and expires_at. Use Secure, HttpOnly cookies with an appropriate SameSite policy and narrow scope. Rotate identifiers after login and privilege changes. Enforce idle and absolute timeouts on the server. Logout must revoke server-side state.

Access-control models

RBAC assigns permissions through roles; ABAC evaluates attributes such as tenant or resource ownership; relationship-based rules model shared access. Default deny. Verify permissions for every API request, object read, download and mutation. Hiding an admin button is not authorization. Do not accept roles or tenant identifiers from the browser without validating them against session membership.

Browser and API boundaries

Use CSRF protection for cookie-authenticated state changes, validate Origin where appropriate and restrict CORS to intended origins. CORS is not an authentication layer. Keep long-lived bearer tokens out of browser-accessible storage when a secure cookie session fits the architecture. Validate JWT signatures and claims; plan key rotation and revocation rather than merely decoding tokens.

Acceptance checks

Test cross-tenant object IDs, revoked sessions, expired cookies, role downgrade, logout on another device, CSRF attempts, forged JWTs and direct privileged endpoints. Log decisions with correlation IDs while excluding raw tokens. Reauthenticate before sensitive exports, payment changes and factor enrollment.

6. Implementation Pattern and Copyable Code

This focused TypeScript implementation belongs in the trusted application or test layer. Supply identity, permission and provider-verification state from real verified dependencies; do not accept trust flags directly from a browser.

typescript
interface Session {
  userId: string;
  tenantId: string;
  revokedAt: number | null;
  expiresAt: number;
  permissions: ReadonlySet<string>;
}
export function authorize(
  session: Session,
  resourceTenant: string,
  requiredPermission: string,
  now: number
): void {
  if (session.revokedAt !== null || session.expiresAt <= now) {
    throw new Error("Session expired or revoked");
  }
  if (session.tenantId !== resourceTenant ||
      !session.permissions.has(requiredPermission)) {
    throw new Error("Access denied");
  }
}

Version the implementation with the consuming application and run this chapter’s acceptance checks when its assumptions change. A copied unit does not establish that all external integrations are active.

10. Operations, Ownership and Maintenance

Assign a technical owner for sessions & authorization. Review changes to Secure cookies, Application database, Policy engine against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
