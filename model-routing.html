1. Description, Purpose and Boundaries

Route compatible requests to approved models within budget and policy.

Route by required capability and validated performance, then optimize cost. Treat model outputs and proposed tool calls as untrusted.

Treat model routing & evaluation as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Reserve budget and invoke approved adapter. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize fallback weakens data policy and timeout releases budget despite uncertain charge. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, validate output and settle or reconcile usage, rather than merely observing request acceptance.

5. Detailed Mechanics and Topic Features

Selection contract

Record task type, required modalities, structured schema, allowed tools, context budget, data classification, latency SLO and spend ceiling. Filter incompatible models before ranking candidates. Use the least expensive candidate that meets the measured quality bar; escalate only when policy and budget permit.

Registry and fallbacks

Store provider, exact model ID, version or snapshot, verified capabilities, region, quotas, evaluation version, approved_at and rollback target. Distinguish transient capacity errors from unsupported requests and policy refusals. Do not use a fallback that weakens privacy, tool permissions or output schema.

Evaluation rubric

Measure task correctness, grounded citations, tool argument validity, injection resistance, schema adherence, latency, cost and refusal appropriateness. Use paired task comparisons and enough representative examples; report uncertainty. A self-rating by the generating model is not a substitute for an independent acceptance test.

RAG, tuning and long context

Use retrieval for changing or private knowledge with access filtering and provenance. Use fine-tuning only when measured behavior/style improvements justify dataset and maintenance costs. Use long context when the task needs it and test lost-in-context failures. Neither retrieval nor fine-tuning guarantees factuality.

Deployment gate

Require approved evaluations, capability checks, bounded tool execution, telemetry, rollback and a human owner. Track drift on production-like samples. Model changes must not alter account authorization or allow retrieved instructions to override policy.

6. Implementation Pattern and Copyable Code

This focused TypeScript implementation belongs in the trusted application or test layer. Supply identity, permission and provider-verification state from real verified dependencies; do not accept trust flags directly from a browser.

typescript
type Capability = "text" | "vision" | "json";
interface Candidate {
  id: string;
  approved: boolean;
  capabilities: ReadonlySet<Capability>;
  privateDataAllowed: boolean;
}
export function compatibleCandidates(
  candidates: readonly Candidate[],
  required: readonly Capability[],
  includesPrivateData: boolean
): Candidate[] {
  return candidates.filter(candidate =>
    candidate.approved &&
    (!includesPrivateData || candidate.privateDataAllowed) &&
    required.every(capability => candidate.capabilities.has(capability))
  );
}

Version the implementation with the consuming application and run this chapter’s acceptance checks when its assumptions change. A copied unit does not establish that all external integrations are active.

7. Detailed Mermaid Architecture, Process and Explanations

The diagram shows ordered work, review gates, observability, rejection paths and manual ownership. It is a design reference rather than proof of an active service.

Step-by-step diagram descriptions

  1. 1. Receive scoped inference request: Define the objective, owner, tenant and versioned starting evidence.
  2. 2. Classify difficulty sensitivity and context: List source systems, integration contracts, provenance and test inputs.
  3. 3. Evaluate routing policy and spend threshold: Apply the chapter-specific quality, safety, privacy and approval gates.
  4. 4. Select permitted model and tool configuration: Execute the controlled operation with tracing, limits and documented contracts.
  5. 5. Run inference with bounded fallback: Inspect measurable outputs, negative cases, dependency failures and recoverability.
  6. 6. Record quality latency and cost outcomes: Publish reviewed results, criteria and decisions, preserving redacted trace evidence.
  7. 7. Exception handling: Stop unsafe processing, reconcile previously committed effects, and permit only bounded retries or tested rollback.

10. Operations, Ownership and Maintenance

Assign a technical owner for model routing & evaluation. Review changes to Model registry, Budget ledger, Model adapter against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
