Daily Reference Updates

1. Description, Purpose and Boundaries

The knowledge-center-updates Worker refreshes the source-evidence panel for every registered chapter once per day. Static HTML remains the authoritative technical narrative. The Worker independently retrieves public references, records a bounded source outline and exposes its results through read-only JSON endpoints.

The service does not execute a language model, rewrite chapter prose, modify code, send email or commit to GitHub. A detected title or heading change signals that an editor should review the affected narrative. This distinction prevents an automated availability check from being presented as verified technical advice.

2. Architectural Principles and Decisions

The static site and updater have separate release and failure boundaries. A source outage or unavailable Worker must not prevent reading the complete chapter. Browser requests contain only the public chapter identifier. No credentials or private chapter content are sent to the updater.

The registry fixes chapter IDs and reference URLs at deployment. Readers cannot supply arbitrary URLs, trigger refreshes or mutate state. Fetches require HTTPS, reject unapproved destination hosts, follow at most two approved redirects and apply an eight-second timeout plus a 256 KiB document-prefix limit. The comparison covers the title and first five main-content headings when available; it is not a complete semantic or code diff.

3. Process, Inputs and Outputs

StepInputOperation and output
1Scheduled UTC timestampUTC minute selects chapter order 0–25. The UTC hour must be zero.
2Registered references and previous KV stateSend conditional GET using saved ETag/Last-Modified validators when present.
3Source responseAccept HTML/plain-text responses with an extractable outline; classify redirects, HTTP errors, timeout and unsupported formats explicitly.
4Title and main headingsHash the normalized outline. Record baseline, unchanged, outline_changed or check_failed.
5Per-chapter source recordsPersist current state and a seven-entry chapter check history; retain last successful source metadata on failure.
6Read-only API responseRender timestamps and source states in the chapter’s Daily Reference Updates section.

A successful check on the same UTC date is idempotent. A failed or partial check may be retried by a scheduled event during that date, but normal readers cannot request one. KV is eventually consistent: this daily low-write workload does not use KV as a lock, a payment ledger or an exactly-once coordinator.

worker.mjs embeds the deployed registry to keep scheduled runs independent of GitHub availability. config/chapters.json is the human-readable registry used by navigation and search maintenance. When adding a chapter, keep its order unique, extend the Cron minute range, update the embedded registry, deploy the Worker and rebuild the static search index.

Every KV record uses chapter:<chapter-id>. checkedAt records the last attempt; lastSuccessfulCheckAt requires all mapped sources to succeed. Each source has its own lastSuccessAt and optional lastChangeAt. An HTTP error must not overwrite those dates with a false successful timestamp. A first successful observation creates a baseline and does not imply a newly released feature.

The public endpoints are GET /health, GET /v1/chapters and GET /v1/chapters/<registered-id>. All mutations are internal to scheduled(). Unknown chapter IDs return 404, non-read methods return 405, and unapproved browser origins return 403. CORS is a browser constraint, not authentication; the returned data is intentionally public.

async function digest(value){
 const bytes=await crypto.subtle.digest("SHA-256",new TextEncoder().encode(JSON.stringify(value)));
 return [...new Uint8Array(bytes)].map(b=>b.toString(16).padStart(2,"0")).join("");
}

7. Detailed Mermaid Architecture, Process and Explanations

Expanded chapter-specific architecture from initial request to policy evaluation, bounded execution, verification and controlled recovery.

Descriptions of each processing stage

  1. 1. Accept HTTPS request at Cloudflare Worker: Identify input owner, request scope, correlation ID and expected acceptance criteria.
  2. 2. Validate token schema tenant and request body: Establish allowed identity state and authoritative user or tenant ownership.
  3. 3. Resolve approved bindings limits and secrets: Evaluate data privacy, security policies, resource limits and downstream contracts.
  4. 4. Route synchronous work or durable queue job: Execute only approved actions with explicit service boundaries and short-lived privileges.
  5. 5. Check downstream response and retry state: Preserve idempotency keys and verify each tool or worker outcome before changing state.
  6. 6. Return response and record operational telemetry: Check final response, record versioned audit evidence and capture measurable quality and operational metrics.
  7. 7. Recovery: Stop new side effects while state is uncertain; reconcile external operations, then retry within limits or escalate to an owner.

8. Failure Modes, Edge Cases and Security

ConditionRequired behavior
Source returns 403, 404, 429 or 5xxRecord check_failed and preserve last good metadata. Do not report the chapter as fully checked.
Server returns 304 with a known digestKeep the saved outline and update only the successful check evidence.
Unapproved redirect or unsupported bodyReject; never follow arbitrary reader-supplied destinations.
Document prefix omits main contentReport unavailable outline if no title exists; when only a title is available, the comparison remains limited.
Provider changes body text without changing compared headingsThe checker may report unchanged. Editorial review still covers code and detailed claims.
KV write or Worker execution failsCron is recorded as failed by the platform; the previous persisted report remains. Inspect observability and capacity.
Browser cannot fetch live dataLeave the HTML narrative and reference links intact and show a service-unavailable message.
Duplicate scheduled invocationSame-day successful records are reused. Eventual consistency means duplicate network checks remain possible.

No paid model or subscription is enabled by this implementation. Free-tier usage is bounded by one scheduled chapter per minute, at most three sources per chapter and one state write per chapter. Provider redirects increase subrequest count; each source is limited to two redirects. Free-tier limits are shared with other account workloads and can still cause failed checks. Do not automatically upgrade billing.

Unit tests verify application logic with deterministic fixtures. They cannot prove that external sites allow the Worker’s network identity or that a future Cron run stays within resource limits. Track those as live operational evidence, not as completed by a mocked test.

10. Operations, Ownership and Maintenance

Inspect the Worker’s scheduled-event history and logs for the chapterId, status, source count and failed count. Logs contain no page body or credential. Investigate reports older than 36 hours, repeated source errors and missing per-chapter state. A red source status is a maintenance signal, not a reason to replace the last good technical narrative automatically.

To change a URL, review the new official source, update the registry and redeploy the Worker. To roll back, deploy the preceding approved worker.mjs and restore its compatible schedule; do not delete KV history. To disable checks, remove the Cron Trigger while leaving read-only data available. KV records are retained until deliberately removed; only the seven most recent per-chapter run summaries are retained in the history array.
