1. Description, Purpose and Boundaries

Choose components around trust boundaries, consistency and recovery.

Treat phase 2: system architecture as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Choose storage, transport and execution contracts. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize assuming all stores are strongly consistent and giving agents unrestricted credentials. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, review failure and rollback paths, rather than merely observing request acceptance.

3. Process, Inputs and Outputs

1Document identity and data boundariesApproved input scope, source and owner

Stop at any boundary whose required evidence cannot be established. If an external side effect may already have occurred, reconcile its durable identity before retrying.

  context: OperationContext,
  permission: string

  if (!context.permissions.has(permission)) {
    throw new Error("Permission denied");

10. Operations, Ownership and Maintenance

Assign a technical owner for phase 2: system architecture. Review changes to Cloudflare Workers, D1 or PostgreSQL, Queues against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
