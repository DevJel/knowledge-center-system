1. Description, Purpose and Boundaries

Prove identity using a verified provider or application-owned sign-in flow.

Authentication proves identity; authorization decides what that identity can do. Keep the two responsibilities explicit.

Treat authentication & sso as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Resolve verified identity to active membership. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize account linking trusts unverified email and recovery bypasses the primary factor. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, create a session at the required assurance level, rather than merely observing request acceptance.

3. Process, Inputs and Outputs

Stop at any boundary whose required evidence cannot be established. If an external side effect may already have occurred, reconcile its durable identity before retrying.

5. Detailed Mechanics and Topic Features

Methods and tradeoffs

Passwords require secure password hashing, recovery and abuse controls. Email OTP proves current access to a mailbox and is not phishing-resistant. Magic links are bearer credentials that can leak through forwarded messages. TOTP uses authenticator-generated time codes; recovery codes need protected storage and one-time consumption. Passkeys use WebAuthn and origin binding. OIDC provides federated sign-in; OAuth alone is delegated authorization. SAML supports enterprise federation.

Role-specific policy

Create an explicit policy matrix for administrator, user, employee, client, applicant and demo roles. For the user’s projects that specify Duo-only administration, enforce the Duo SSO flow server-side and do not expose an alternative route that bypasses it. Other projects may have different approved policies; do not copy a single app’s policy globally. Employee application SSO and administrator Cloudflare Access protections are separate architectural decisions.

Federated sign-in checklist

Use supported identity-provider libraries. Validate issuer, audience, signature, expiry, state and nonce where applicable; use PKCE for authorization-code flows. Allowlist redirect URIs. Link accounts only after proving control of the identities; matching an unverified email is insufficient. Apply application roles after identity verification and fail closed if provider checks fail.

Enrollment and recovery

Require reauthentication for factor changes, email changes and account linking. Notify users of security changes. Protect recovery paths as strongly as sign-in and audit privileged recovery. Plan lost-device recovery, provider outage behavior, account suspension and session revocation. Test denied users, stale roles, invalid callbacks and blocked direct API requests.

6. Implementation Pattern and Copyable Code

This focused TypeScript implementation belongs in the trusted application or test layer. Supply identity, permission and provider-verification state from real verified dependencies; do not accept trust flags directly from a browser.

typescript
interface VerifiedIdentity {
  issuer: string;
  subject: string;
  emailVerified: boolean;
}
interface Membership {
  userId: string;
  tenantId: string;
  active: boolean;
}
export function resolvePrincipal(
  identity: VerifiedIdentity,
  membership: Membership,
  approvedIssuers: ReadonlySet<string>
) {
  if (!approvedIssuers.has(identity.issuer) || !identity.subject) {
    throw new Error("Unapproved identity");
  }
  if (!membership.active) throw new Error("Inactive membership");
  return { userId: membership.userId, tenantId: membership.tenantId };
}
// Invoke only after the provider library verifies signatures,
// audience, expiry and authentication-transaction protections.

Version the implementation with the consuming application and run this chapter’s acceptance checks when its assumptions change. A copied unit does not establish that all external integrations are active.

8. Email OTP architectureGenerate a cryptographically random purpose-bound code server-side, store only a salted keyed digest, bind it to user/session/change context, set a short TTL and strict single-use semantics, rate-limit issuance and verification, and use generic responses to prevent account enumeration. Deliver through a verified email sender, handle suppression/bounces and monitor abuse. Log no plaintext code.Check expired, replayed, wrong account, incorrect, throttled and parallel-redemption cases. OTP authorizes only its intended transaction, not arbitrary account or privilege changes.
9. Regular-user passkeysImplement WebAuthn passkey registration and authentication only for ordinary users. Verify challenge origin, RP ID, credential public key, authenticator data, signed assertion and replay safeguards server-side; enforce user-verification requirements appropriate to account risk. Provide secure recovery without bypassing ownership checks.Admin passkey registration and admin login must remain unavailable. Test cross-origin, replay, stolen-session and recovery abuse.
10. Authorization and session issuanceAfter verified sign-in, rotate to a new secure session with HttpOnly, Secure and SameSite cookie attributes; set explicit absolute and idle expiry, CSRF defenses, tenant and role authorization on EVERY privileged request, revocation and step-up where required. Acceptance and rollout checklist

  1. Choose Duo Web SDK v4 for post-primary MFA or Duo SSO for federation; document the distinction.
  2. Configure approved Duo tenant, integration type, policy, redirect and client credentials.
  3. Provision an exact identity mapping and enroll a test Duo Mobile device.
  4. Test all four login paths: admin Duo push, admin email OTP, user email OTP and user passkey.
  5. Verify guest first prompt continues only after a successful authorized session.
  6. Verify nonce/state/PKCE or SAML anti-replay as applicable and reject mismatches.
  7. Verify push denial, timeout, unapproved factors, provider outage and unknown user all fail closed.
  8. Verify session rotation, tenant isolation, revocation and logging without secrets.
  9. Run release and rollback drills and record operator approval.

7. Detailed Mermaid Architecture, Process and Explanations

This flow describes the request lifecycle, security checks, execution, retries and durable evidence for this chapter. It is implementation guidance, not a deployed-system claim.

What each stage does

  1. 1. Select account type and method: Capture caller, purpose, tenant or user identifier, correlation ID and data classification.
  2. 2. Guests complete first prompt before login: Apply prerequisite checks before initiating any irreversible action.
  3. 3. Admin uses Duo push or email OTP; user uses passkey or email OTP: Enforce the listed restrictions on the server; test valid, expired, repeated and cross-tenant requests.
  4. 4. Validate challenge TTL attempts origin and purpose: Perform only explicitly permitted work using short-lived credentials and bounded timeouts.
  5. 5. Create least-privilege session: Save the state transition and capture a durable operation or idempotency identifier.
  6. 6. Redirect to dashboard and log outcome: Prove the resulting behavior with redacted audit records and automated acceptance tests.
  7. 7. Failure and rollback: Do not blindly repeat side effects. Reconcile committed work, cap retries, and raise incidents when the state is uncertain.

14. Senior Engineering Walkthrough: Practical Implementation

Purpose: Authentication proves identity; federation delegates identity to a trusted provider; MFA adds another factor; authorization is a separate server-side decision. Duo Universal Prompt for MFA is not automatically Duo SSO federation.

14.1 Worked scenario

A sequential sign-in may verify password, issue and atomically consume an email OTP, complete Duo Universal Prompt, then rotate and issue a session. Bind all steps to one short-lived login transaction and the same user; do not create a fully authenticated session after only one factor.

14.2 Implementation sequence

  1. Verify password
  2. create transaction
  3. send OTP
  4. verify and consume OTP once
  5. start Duo MFA
  6. validate signed callback/result and transaction binding
  7. apply risk and account status checks
  8. rotate session
  9. record factor assurance
  10. support secure recovery

14.3 Example contract and code

Pseudocode: verifyPassword(userId,password); verifyAndConsumeEmailOtp(transactionId,code); verifyDuoPrompt(transactionId,duoResult); createRotatedSession(userId). Each function is server-side and fails closed.

Illustrative implementation
// Sequential factors bound to one server-side login transaction
await verifyPassword(userId, password);
await verifyAndConsumeEmailOtp(transactionId, code);
await verifyDuoUniversalPrompt(transactionId, duoResult);
await sessions.createRotated(userId);

14.6 Senior review checklist

  • Inputs are validated and treated as untrusted.
  • Authentication and resource-level authorization are enforced server-side.
  • Data ownership, retention, tenant isolation and secret handling are explicit.
  • Timeouts, retries, idempotency, partial failure and rollback are documented.
  • Normal, boundary, abuse and recovery paths are tested.
  • Operational ownership, monitoring and maintenance are assigned.
