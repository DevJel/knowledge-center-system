1. Description, Purpose and Boundaries

Prove identity using a verified provider or application-owned sign-in flow.

Authentication proves identity; authorization decides what that identity can do. Keep the two responsibilities explicit.

Treat authentication & sso as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Resolve verified identity to active membership. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize account linking trusts unverified email and recovery bypasses the primary factor. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, create a session at the required assurance level, rather than merely observing request acceptance.

5. Detailed Mechanics and Topic Features

Methods and tradeoffs

Passwords require secure password hashing, recovery and abuse controls. Email OTP proves current access to a mailbox and is not phishing-resistant. Magic links are bearer credentials that can leak through forwarded messages. TOTP uses authenticator-generated time codes; recovery codes need protected storage and one-time consumption. Passkeys use WebAuthn and origin binding. OIDC provides federated sign-in; OAuth alone is delegated authorization. SAML supports enterprise federation.

Role-specific policy

Create an explicit policy matrix for administrator, user, employee, client, applicant and demo roles. For the user’s projects that specify Duo-only administration, enforce the Duo SSO flow server-side and do not expose an alternative route that bypasses it. Other projects may have different approved policies; do not copy a single app’s policy globally. Employee application SSO and administrator Cloudflare Access protections are separate architectural decisions.

Federated sign-in checklist

Use supported identity-provider libraries. Validate issuer, audience, signature, expiry, state and nonce where applicable; use PKCE for authorization-code flows. Allowlist redirect URIs. Link accounts only after proving control of the identities; matching an unverified email is insufficient. Apply application roles after identity verification and fail closed if provider checks fail.

Enrollment and recovery

Require reauthentication for factor changes, email changes and account linking. Notify users of security changes. Protect recovery paths as strongly as sign-in and audit privileged recovery. Plan lost-device recovery, provider outage behavior, account suspension and session revocation. Test denied users, stale roles, invalid callbacks and blocked direct API requests.

6. Implementation Pattern and Copyable Code

This focused TypeScript implementation belongs in the trusted application or test layer. Supply identity, permission and provider-verification state from real verified dependencies; do not accept trust flags directly from a browser.

typescript
interface VerifiedIdentity {
  issuer: string;
  subject: string;
  emailVerified: boolean;
}
interface Membership {
  userId: string;
  tenantId: string;
  active: boolean;
}
export function resolvePrincipal(
  identity: VerifiedIdentity,
  membership: Membership,
  approvedIssuers: ReadonlySet<string>
) {
  if (!approvedIssuers.has(identity.issuer) || !identity.subject) {
    throw new Error("Unapproved identity");
  }
  if (!membership.active) throw new Error("Inactive membership");
  return { userId: membership.userId, tenantId: membership.tenantId };
}
// Invoke only after the provider library verifies signatures,
// audience, expiry and authentication-transaction protections.

Version the implementation with the consuming application and run this chapter’s acceptance checks when its assumptions change. A copied unit does not establish that all external integrations are active.

10. Operations, Ownership and Maintenance

Assign a technical owner for authentication & sso. Review changes to Duo, WebAuthn, OIDC provider against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
