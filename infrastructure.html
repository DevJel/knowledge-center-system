Cloud, DNS & Secrets

VersionReviewedArchitecture scope
2.0.02 November 2026Separate DNS, hosting, runtime resources and credential ownership.

1. Description, Purpose and Boundaries

Separate DNS, hosting, runtime resources and credential ownership.

Keep source, deployment, DNS, runtime resources and credentials as separate layers with explicit ownership.

Treat cloud, dns & secrets as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Provision least-privilege secrets and domain mapping. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize dns record changed in wrong account and public build contains private credential. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, verify tls, runtime health and release ownership, rather than merely observing request acceptance.

5. Detailed Mechanics and Topic Features

Deployment model

GitHub holds source and CI. This knowledge center itself is static GitHub Pages with Cloudflare DNS. A future interactive app may use Cloudflare Workers or Pages Functions for API execution, resource bindings for data and an SMTP-capable backend for SES. Confirm runtime TCP/TLS and library support before choosing a mail implementation. Static HTML cannot safely send authenticated SMTP.

Environment and bindings

Maintain separate production/demo/staging databases, buckets, sessions and secrets. Record resource IDs and binding names in non-secret configuration. Use a managed secret store with scoped runtime access and a documented rotation procedure. Store SMTP username/password, OTP HMAC key, signing keys and provider client secrets server-side. Public Turnstile site keys are distinct from secret verification keys.

DNS and TLS

Use the hosting provider’s required custom-domain mapping. GitHub Pages CNAME targets the account’s github.io hostname; Cloudflare Pages uses the project’s pages.dev hostname and an attached Pages custom domain. Confirm domain ownership, DNS resolution, certificate issuance and HTTPS redirects separately. Avoid changing unrelated mail or production records during a web-domain fix.

Release controls

Review → validate → build → stage → migrate compatibly → deploy → smoke-test → observe. Keep rollback instructions and avoid incompatible schema rollback. Pin dependencies and scan for secrets. Preserve existing production access controls until replacement authentication is implemented and tested. Document any paid resource before enabling it.

10. Operations, Ownership and Maintenance

Assign a technical owner for cloud, dns & secrets. Review changes to Cloudflare DNS, GitHub Pages, Secret Store against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
