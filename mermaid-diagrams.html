1. Description, Purpose and Boundaries

Maintain versioned diagrams as editable documentation rather than opaque artwork.

Treat mermaid diagrams as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Author and validate source against the architecture. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize diagram drifts from actual deployment and external renderer unavailable. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, render preview and publish copyable markdown, rather than merely observing request acceptance.

10. Operations, Ownership and Maintenance

Assign a technical owner for mermaid diagrams. Review changes to Mermaid, GitHub Markdown, Git history against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
