1. Description, Purpose and Boundaries

Deliver transactional messages with authenticated senders and traceable outcomes.

Use a backend delivery service and observable queues. Keep transactional security messages distinct from marketing campaigns.

Treat email sending & deliverability as an independently reviewable capability. Trace its inputs, processing decisions and acceptance evidence before applying it to a live system. The examples define bounded units; external services need separately verified permissions, contracts and environment configuration.

2. Architectural Principles and Decisions

The primary decision boundary is: Claim outbox job and send over authenticated TLS. Application logic and an accountable owner establish this decision. Preserve the input identity and rule revision so its outcome can be investigated.

Prioritize smtp accepted mistaken for inbox delivered and ambiguous timeout produces duplicate email. Establish checks for these failures before enabling automation. Completion requires evidence for the final step, process delivery events and suppression, rather than merely observing request acceptance.

5. Detailed Mechanics and Topic Features

SES SMTP configuration

For the established Sydney setup, configure email-smtp.ap-southeast-2.amazonaws.com with port 587 and STARTTLS. Require TLS and certificate validation. SES SMTP credentials differ from AWS access keys and are region-specific. Verify the sender identity, account production-access status and current sending quotas in the same region. Never embed SMTP credentials in browser code or publish them in the knowledge center.

Domain authentication

Configure DKIM using the provider-issued records. Set SPF for the actual envelope sender; do not create multiple SPF records at one name. Publish DMARC with a monitored rollout and verify alignment. If using a custom MAIL FROM domain, use its exact region-specific MX/SPF instructions. Distinguish visible From, Reply-To, envelope MAIL FROM and return-path roles. DNS examples must not replace provider-issued values.

Email catalog

Plan verification, sign-in OTP, welcome, password reset, security-change notification, invitation, application confirmation, inquiry confirmation, receipt and operational alert templates. Include an identifiable sender, purpose, expiry when relevant and support information. Send both plain text and HTML, use readable contrast and accessible structure, and avoid exposing sensitive data in subjects. Keep marketing content out of OTP messages.

Outbox and delivery events

Write the application event and outbox record transactionally when possible. A worker claims the job, checks expiry/suppression and sends via SMTP. Record the provider message ID, attempts and next retry. Retry transient failures with backoff and jitter; stop on permanent rejection. SMTP acknowledgement means accepted for processing, not inbox delivery. An ambiguous timeout can cause duplicates; use application deduplication but do not promise exactly-once SMTP delivery.

Operations and diagnostics

Handle provider bounce and complaint events through an authenticated, validated event path; deduplicate events and update suppression. Track queue age, send failure, bounce/complaint rates and accepted-to-delivered outcomes where available. Diagnose missing OTP by correlation ID: request → challenge → outbox → SMTP response → provider event → recipient filtering. Check region, credentials, identity, sandbox restrictions, suppression, quota and spam folder without logging the message’s code.

6. Implementation Pattern and Copyable Code

This focused TypeScript implementation belongs in the trusted application or test layer. Supply identity, permission and provider-verification state from real verified dependencies; do not accept trust flags directly from a browser.

typescript
export interface TransactionalMail {
  operationId: string;
  recipient: string;
  template: "login_otp" | "security_notice" | "invitation";
  expiresAt: number;
}
export function shouldAttempt(
  mail: TransactionalMail,
  now: number,
  suppressed: boolean,
  attempts: number
): boolean {
  if (suppressed || mail.expiresAt <= now) return false;
  if (!Number.isSafeInteger(attempts) || attempts < 0) return false;
  return attempts < 5;
}
export const smtpTransportPolicy = {
  host: "email-smtp.ap-southeast-2.amazonaws.com",
  port: 587,
  requireStartTls: true,
  validateServerCertificate: true
} as const;

7. Detailed Mermaid Architecture, Process and Explanations

This flow describes the request lifecycle, security checks, execution, retries and durable evidence for this chapter. It is implementation guidance, not a deployed-system claim.

What each stage does

  1. 1. Receive approved email event: Capture caller, purpose, tenant or user identifier, correlation ID and data classification.
  2. 2. Validate recipient and template: Apply prerequisite checks before initiating any irreversible action.
  3. 3. Queue stable idempotency key: Enforce the listed restrictions on the server; test valid, expired, repeated and cross-tenant requests.
  4. 4. Send via verified AWS SES identity: Perform only explicitly permitted work using short-lived credentials and bounded timeouts.
  5. 5. Classify bounce complaint and transient failures: Save the state transition and capture a durable operation or idempotency identifier.
  6. 6. Reconcile delivery and suppression: Prove the resulting behavior with redacted audit records and automated acceptance tests.
  7. 7. Failure and rollback: Do not blindly repeat side effects. Reconcile committed work, cap retries, and raise incidents when the state is uncertain.

10. Operations, Ownership and Maintenance

Assign a technical owner for email sending & deliverability. Review changes to Amazon SES SMTP, DNS provider, Queue worker against this chapter’s assumptions. Record the dependency contract, environment and last tested revision.

Use the failure matrix to locate uncertain state during incidents. Preserve redacted evidence, restore the approved configuration or apply a reviewed correction, and rerun acceptance checks. Update the review date after provider or architectural changes.
